Supabase's [identity-linking documentation][1] describes automatic same-email linking; its [passwordless documentation][3] explains redirect allow-lists and one-time magic-link behavior. The [PostgreSQL math reference][2] distinguishes `round(numeric, integer)` from single-argument `round(double precision)`. These references explain the gates; they do not replace a staging/live test of this app.

## Owner decisions and feasibility update

- Require email confirmation for new password accounts **after** staging and existing-account checks; do not change production Auth settings yet.
- Replace the unvalidated 2–4-week multiplication with current-only matched, dated advertised-specials comparisons and explicit chain coverage. A read-only October 17 production query found 5,068 date-valid offer rows across nine chains but only **235** exact normalized name/brand/canonical-pack/price-basis cohorts present at two or more chains, and none at three or more. Of their 472 underlying rows, 112 have a nonblank promo (often a quantity-dependent `2/$4.00`-style price); excluding numeric multi-buy promos leaves **179** eligible single-item cohorts across two chains, zero across three or more. This supports a narrow selected-specials comparison, not a whole-basket, universal chain ranking, or forecast. Abstain if manual QA finds false matches.
- Use Google Cloud project `gen-lang-client-0507313380` (project number `734247762212`) for the OAuth client. This is only a project selection, **not** a configured client or provider: the local browser-profile copy was locked by the running Brave process, the isolated browser reached a Google login wall without a matching saved account, and the local `gcloud` CLI was not installed. Do not work around access controls or invent a client secret. Authorized project access and the provider settings readback remain open.
- Work on branch `release/full-readiness-20261017` under the gated implementation plan `.hermes/plans/2026-10-17_223607-full-release-hardening.md`; neither a branch nor a passing local test authorizes a deployment.

**Local branch progress, not a release verdict:** The uncommitted candidate now gates unsafe providers, adds recovery/callback review and a current-only `/api/analytics/comparable_offers` endpoint, and fixes tested batch/rollback/replay accounting and pack-aware dedup in the weekly/backfill paths. Both dashboard copies are byte-identical. The integrated local suite passed **123 tests, 12 skipped**; isolated SQLite/Postgres ingestion and analytics checks passed in disposable containers. Anonymous browser checks of the localhost dashboard at 320px/375px had no page-level horizontal overflow, and the currently disabled public Google/signup settings hid those tabs. The local SQLite snapshot had 614 active offers, 3 active chains and 1 eligible cohort. These checks do **not** verify protected Netlify return paths, real email-confirmation/recovery/OAuth identities, concurrent ingestion or full production data quality. This first local pass did not include adversarial review; keep NO-GO until the remaining gates are closed.

**Adversarial review after the first local integration:** A separate read-only browser review reproduced cross-tab magic-link rejection (intent was tab-local), a root callback that drops the correlation query, same-account/recovery callbacks rejected when an old session exists, an expired access token that discards a usable refresh token, and quantity-dependent `2x1` offers admitted by an `N/`-only filter. A separate SQLite review reproduced four ingestion failures that the first 123-test run missed: distinct brand/SKU/promo offers discarded by the existing unique key, database-wide insert failures reported as successful runs, nullable replay across different pages, and cross-run dedup that invalidates a prior completed run's count. The reviewers did not run new Postgres repros. These findings **reopened** the Auth/analytics/DB gates; passing tests alone is not a full-release approval.

**Post-review candidate, still NO-GO:** Regression tests now cover cross-tab/root Auth callbacks, same-user recovery and refresh, explicit different-account review, quantity-dependent `2x1`/`2 x 1`/`2 por 1` exclusion in both API and UI, and empty/interrupted structured pagination. The new read-only comparable endpoint uses a scoped connection without per-request schema DDL; **legacy API endpoints still run `_conn()` and need a lifecycle fix before release**. Ingestion now fails closed on incompatible legacy-key collisions and database-wide failures, avoids provenance-based nullable replays, and limits canonical dedup to the current run. A Postgres identity migration is **draft-only**; the legacy SQLite/production constraints do not preserve all distinct variants. The local full suite passed **155 tests, 27 skipped** after dashboard-copy synchronization. An independently started disposable PostgreSQL container ran the focused DB/API/pagination suite (**64 passed, 4 skipped**) and was stopped. Local 320px/375px layout checks found no document overflow; disabled Google/signup UI stayed hidden. These are not real provider or password-gated Netlify return checks. The historical “Mayores bajas de la semana” card was removed from the candidate after a local example displayed a 92.9% apparent drop from normalized-name minimum sale prices across editions/possible packs; `/api/movers` remains a legacy endpoint and is not a validated same-item savings metric.

**Second adversarial pass:** Mocked-browser repros found a cross-account pending-list POST: an A-authorized request returning 401 retried with B's token after an account switch, without B's review; another tab could approve A after shared storage switched to B. Cross-device recovery was rejected and a same-user refreshed list response was discarded. Disposable DB repros found a concurrent legacy-key collision still reported `ok`, current-run dedup deleting different raw/category products, and a partly rejected batch reported `ok`. The specials API/UI also admitted `Oferta 2/$4` and `2x$3`, and its DB-UTC date could be tomorrow in Puerto Rico. These were **additional release blockers** not covered by the 155-test pass. Follow-up regressions now bind pending writes to the initiating account across retries, storage changes and completion; require explicit verified-user confirmation for cross-device recovery; accept same-account refresh responses; detect post-insert legacy collisions, retain raw/category distinctions, and fail the entire run on any rejected row. Both API and UI filter the new promo variants; the endpoint uses the Puerto Rico calendar date independent of the production DB's confirmed UTC session. The dashboard copies were resynchronized and the full local suite passed **174 tests, 33 skipped**. A separately started disposable PostgreSQL container with both DB/API integration DSNs passed **82 tests, 4 skipped**; it was stopped. Real protected Auth behavior, a production-snapshot migration rehearsal and external provider configuration remain unverified.

**Migration preflight (read-only):** Production has 12,776 offers: 829 missing size text, 735 missing brand, 3,761 missing SKU, and none missing normalized name, sale price or edition start. The existing unique constraint is `(chain_slug, product_norm, size_text, price_sale, valid_from)`. A stricter stable-identity grouping found no duplicate groups in the current data, but this does not prove a new unique constraint can be applied without testing a full isolated copy, nor recover distinct variants silently dropped on earlier runs. No production migration is authorized or executed.

**Audit-path caution:** A local API smoke call inherited a previously exported production `DATABASE_URL`; `_conn()` called `init_db()`, which re-executed the schema's idempotent DDL and committed. This was not a read-only API call. A direct read-only follow-up found the production `offers` count unchanged at 12,776 total / 5,068 date-valid and both expected views present. No production data rows were intentionally changed, but avoid invoking app routes against production for read-only probes; open a dedicated read-only psycopg2 session instead. The exported variable was cleared before all subsequent localhost QA. This route-initialization behavior deserves an explicit release review.
