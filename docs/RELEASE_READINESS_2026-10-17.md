## Blocking findings and acceptance gates

| Area | Evidence in reviewed commit | Required before full release |
|---|---|---|
| Email/password ownership | `api/static/dashboard.html:930-957` exposes signup; current Auth auto-confirms email. Neither email ownership nor recovery was tested. | Decide and stage-test confirmation policy, recovery and rate limits; use isolated throwaway accounts; audit compatibility for existing magic-link accounts before changing production settings. Never accept or store a password in the agent/chat. |
| Redirect and session integrity | `dashboard.html:938-940,966-969` puts `emailRedirectTo` in JSON `options` while calling raw GoTrue REST; Supabase's JS client translates that option into a `redirect_to` request parameter. `:989-999,1364-1367` accepts a callback fragment and can flush queued list writes under the resulting account without correlating a login attempt. The root hash forwarder and site-password challenge remain untested together. | Use a verified redirect request shape; correlate OAuth/callback state, show errors and confirm account transitions before replaying pending edits. Test wrong-account fragments, expired links, duplicate-email identities, new and existing accounts, and actual `/app/` return through the visitor gate without recording tokens. |
| Google OAuth | The dashboard shows Google (`:354-358,984-987`) while `external.google=false`. Supabase can automatically link matching email identities; enabling OAuth before confirming email ownership requires careful review.[1] | Owner-configured Google OAuth consent/client and authorized Supabase callback, then enable the Supabase provider securely (no client secret in Git/chat). Verify allowed return URLs, failed and successful redirects, identity linking, sign-out and provider visibility before enabling the button. |
| Analytics meaning | `api/main.py:405-440` sums cheapest keyword-matched *advertised offers* for whatever staple items each chain covers and labels 2×/4× the current sum as future basket projections in `dashboard.html:479-480,1324-1339`. Category average and normalized-name dispersion compare different item/pack mixes (`api/main.py:337-395`). | Remove future-week claims; if analytics is retained, show a dated **observed-specials-only** snapshot with comparable SKU/pack/unit, explicit missing coverage and source dates. Never rank unequal baskets as cheapest or present these totals as the validated Sprint 5 forecast. The separate **DATOS FICTICIOS** illustrated card remains clearly fictional. |
| Analytics correctness | `normalize/schema_pg.sql:32-34` stores prices as `DOUBLE PRECISION`; `api/main.py:301,316,329,342,367-368` uses two-argument `ROUND` on aggregates, which PostgreSQL supports for `numeric`, not `double precision`.[2] Nullable prices can also make `basket_projections` raise while the global handler returns exception text (`api/main.py:787-789`); the dashboard does not surface non-2xx API responses clearly. | Add a real Postgres integration test and explicit numeric casting or deliberate formatting; reject/skip null-price rows, return generic public 500 messages, escape data interpolated into HTML, and test bad/missing data and partial-coverage behavior. |
| Batch write integrity | `normalize/db.py:195-226` retries rows after a failed `executemany` without rolling back a Postgres transaction or SQLite's earlier partial successes. It can count and catalog rejected rows; the current two DB tests miss failures. `dedup_offers` groups only `(product_norm, price_sale)` (`:139-155`), potentially removing distinct sizes; nullable fields in the uniqueness key allow duplicates (`normalize/schema_pg.sql:47`). | Test valid–invalid–valid batches against SQLite **and** isolated Postgres; use savepoints/rollback before fallback, count actual stored rows, update only their product records, preserve different packs, and define idempotent identity for incomplete offers. Test a failed run and next-chain recovery. Do not run experimental tests against production data. |

Supabase's [identity-linking documentation][1] describes automatic same-email linking; its [passwordless documentation][3] explains redirect allow-lists and one-time magic-link behavior. The [PostgreSQL math reference][2] distinguishes `round(numeric, integer)` from single-argument `round(double precision)`. These references explain the gates; they do not replace a staging/live test of this app.

## Release sequence after fixes and decisions

1. Use test-first, isolated fixes for the DB data-integrity path and analytics Postgres/error path. Add behavior tests that first fail for each reported bug; run the full local suite. Audit the existing scraper dedup behavior separately because it predates the merged batch change and is already present on mt01.
2. Redesign or withhold analytics until chain/item/pack coverage can support each displayed comparison. Keep any current-offer calculation explicitly non-predictive. Review the exact live API/HTML responses on staging, not just source code.
3. Decide the production email-confirmation policy and account migration/recovery behavior. Configure the Google Cloud OAuth client and Supabase provider with the owner in the proper consoles or approved secret store; never paste the client secret into this repo or chat. Test callback correlation and account switching before exposing signup/Google tabs.
4. Stage Fly plus byte-identical dashboard copies; run Postgres integration tests and fresh throwaway-account flows. The owner still needs to test the protected Netlify password → magic link → `/app/` journey; add Google/password equivalents after their providers are ready. Verify owner-scoped lists and explicit assistant-edit confirmations.
5. Only then approve a specific commit for production. Deploy Fly, read back its release/image and health plus new endpoints; verify the Netlify password challenge on `/` and `/app/` before and after its *manual* static deploy; read back its deploy ID and file hash. Keep a rollback target and do not call a passing test suite a completed end-to-end login.
